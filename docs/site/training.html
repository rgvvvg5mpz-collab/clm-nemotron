CLM on Nemotron · clm-train

Train a classifier head on your own labels

clm-train turns a file of labelled examples into a head that clm-serve can serve. The Nemotron encoder stays frozen: every text is embedded once, then only the two small projection heads are trained. On a laptop, 400 labelled tickets take about 16 seconds.

Prefer clicking? Open the playground that clm-serve serves at http://localhost:8700/ and choose Train a model. It walks through the same steps with your file and serves the result as soon as it finishes. This page covers the command line, for scripts and CI.

1

Install, start the encoder, and pick its size

Install the package from the repo: pip install -e . on Linux, pip install -e ".[mac]" on a Mac. That puts clm-train and clm-serve on the path. Training talks to the encoder over HTTP at http://127.0.0.1:8090/v1/embeddings; change it with --embed-url, or pass --offline on a Linux GPU box to embed in-process with vLLM.

--encoderUse it whenStart it with
nemotron-3-embed-1bLaptops and quick iteration (2.3 GB, 2048-d)python tools/local_embed_server.py --encoder nemotron-3-embed-1b
nemotron-3-embed-8bProduction on an NVIDIA GPU (15.9 GB, 4096-d); the default./serve_nemotron3_embed_8b.sh

The head belongs to the encoder it was trained on. Train with the encoder you'll serve with: clm-serve refuses a head from the other size.

Where the test split comes from

  1. --test FILE, a separate file in the same format, wins.
  2. A split column with values train / test.
  3. A directory or Hub dataset laid out as <workflow>/train-*.parquet and test-*.parquet.
  4. Otherwise --test-frac (default 0.2) of the rows is held out.

Pass --group-column (customer, account, incident) so all rows of one group land on the same side of both the test and the validation split. Without it, near-duplicates of one customer can sit on both sides and inflate the score. Option descriptions are what the model matches against, so write them as the guide describes: distinct, evidence-based, no catch-alls.

3

Run it

# one choice question, separate test file
clm-train --data tickets_train.csv --test tickets_test.csv \
  --question "What is this customer conversation primarily about?" --options options.json \
  --encoder nemotron-3-embed-1b --out runs/tickets

# yes/no, held out by customer
clm-train --data escalations.jsonl --type noul --question "A human agent must take over this conversation." \
  --group-column customer --encoder nemotron-3-embed-1b --out runs/escalation

# typed rows with many questions per state: a local file, a directory, or a Hub dataset
clm-train --data LocalLLaMA/typed-decisions --workflow all --encoder nemotron-3-embed-1b --out runs/typed

What happens

  1. Rows are split into train, validation (--val-frac of train, by group) and test.
  2. Every state and option text is embedded once, with the same query: / passage: prompts and truncation clm-serve uses. Vectors are cached in OUT/embeddings/, so a re-run with new hyperparameters embeds nothing.
  3. The state head, action head and logit scale train for up to --epochs. The epoch with the best validation accuracy is kept, and training stops after --patience epochs without improvement.
  4. The kept head is scored once on the test split, next to clm-raw and the majority label.

If the head doesn't beat the majority label, clm-train says so. Don't serve it; work through the guide's What to change when table first. The test score comes from a single split: with 100 test rows, ±5 points is noise.

5

Serve it and ask the same question

The head scores whatever question you send. Send the one it was trained on, from questions.json, with the same option texts.

clm-serve --encoder nemotron-3-embed-1b --ckpt runs/tickets/best_head.pt

import json
from clm import CLMClient
questions = json.load(open("runs/tickets/questions.json"))
r = CLMClient().system_one(state="customer: I was billed twice for my subscription this month.",
                           questions=questions)
r.answers["label"].choice          # 'billing'
r.answers["label"].probabilities   # near 1.0: calibrate before using as a confidence

Trained heads are confident: on the two tickets we tried, the top class came out at 0.999 or more. Before a probability gates anything, fit a temperature and thresholds on held-out data, as the guide's calibration step describes. A changed best_head.pt is reloaded by a running clm-serve on the next request.
