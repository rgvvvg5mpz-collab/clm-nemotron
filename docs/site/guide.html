Solving a classification problem with CLM

You don't prompt CLM the way you prompt a chat model, and you don't fine-tune the model itself. You write a state, a question and option texts, and if zero-shot isn't good enough, you train two small heads on labelled examples. This page covers when to do which.

Use a held-out split to make the probabilities mean something before anything acts on them.

1

Frame the problem as a typed question

Each question is answered independently against the same state, so one request can carry the whole decision (category, urgency, needs-review) in a single call.

Your problemUseYou get
One label from a fixed set (routing, category, disposition)choiceThe best key and a distribution over all keys
An ordered scale (severity, urgency, quality)scoreThe expected level, e.g. 2.23 on a 0–3 rubric, plus the distribution
Is a statement true of this state (fraud, needs a human, duplicate)?noulThe probability that it's true
Many or open-ended candidates (tools, documents, best-of-N answers)rankCandidates sorted best first

Multi-label problems (several tags can apply at once) are one noul per tag, not one choice. A choice softmax always sums to 1 across its options.

2

Write the state: context only

  • Context goes in the state, the question goes in instructions. CLM appends the question after the context, which is the layout the heads were trained on. Repeating the question inside the state only adds noise.
  • Send objects, not JSON strings. A state object or array is rendered as key: value lines because the heads are trained on prose. A pre-serialised JSON string is embedded as raw JSON.
  • Put what decides the label near the end. An over-long state keeps its last tokens (8,192 by default, prompt included), so boilerplate and history belong first.
  • Drop fields that can't matter. IDs, timestamps and hashes take up budget and pull the vector towards things your options never mention.
3

Write the options. This is the prompt.

Each option's description is embedded on its own as a passage and compared against the state + question vector. The description has to read like an answer to that question, in the vocabulary the state uses. The key is only a name for the result; when a description is given, the key is never embedded.

Weak 
"department": {"type": "choice",
  "instructions": "Department?",
  "criteria": {
    "billing":   "Billing department",
    "technical": "Technical department",
    "other":     "Other"}}

The descriptions share one template, so they embed almost alike; "Other" matches everything a little.

Strong 
"department": {"type": "choice",
  "instructions": "Which team should handle this?",
  "criteria": {
    "billing":   "A charge, invoice, refund or payment problem.",
    "technical": "The product is broken, erroring or down.",
    "account":   "Login, password, plan or access changes."}}

Each description names the evidence that would appear in the state, and no two share wording.

  • Make options mutually distinct. Shared boilerplate ("A ticket about …") adds the same vector to every option and shrinks the differences you need.
  • Avoid catch-alls. "Other" or "None of the above" has no content to match. When you need an escape hatch, use a separate noul ("This fits none of the categories") or a threshold on confidence.
  • For score, write parallel, monotonic levels: "Negligible: …", "Low: …", "Moderate: …". The answer is the expected index, so the order must mean something.
  • For noul, give both sides. criteria: {"true": "…", "false": "…"} describing what each case looks like beats the default "Yes. This is true: <statement>".
  • Don't add query: / passage: yourself. clm-serve adds Nemotron's prompts.
4

Try it zero-shot as a smoke test

With no head loaded, clm-serve serves clm-raw: cosine similarity in Nemotron's own space, times a fixed 100. Use it to check the pipeline and to catch badly worded options. Don't use it to judge whether CLM can solve your problem: it ranks by retrieval similarity, which isn't your labelling rule, and its probabilities are uncalibrated (a cosine gap of 0.05 becomes 99%).

python tools/local_embed_server.py --encoder nemotron-3-embed-1b     # Mac; vLLM on a GPU box
clm-serve --encoder nemotron-3-embed-1b                               # no --ckpt: clm-raw

from clm import CLMClient, Choice
r = CLMClient().system_one(state={"thread": [...]}, questions={"department": Choice(...)})
r.answers["department"].choice, r.answers["department"].probabilities

A real example from the 1B in raw mode: for "What causes tides on Earth?" it ranked "Because the Earth is round." (cos 0.365) above "The Moon's gravitational pull." (cos 0.319) at 99% to 1%. The retriever rewards shared words like "Earth". That's why raw mode needs carefully worded options, and why a trained head helps.

5

Label a set and split it honestly

  • Aim for a few hundred labelled states, with at least ~30 per option you care about. Hold out a test split you never tune on.
  • Split by source entity (customer, account, incident), never by row, or near-duplicates leak into the test.
  • Where annotators disagree, keep their distribution: gold.probabilities trains soft targets, which teaches the head that "urgency 2 or 3" is a real answer.

The trainer reads parquet files in the LocalLLaMA/typed-decisions layout, <workflow>/train-*.parquet and test-*.parquet, with one row per state:

id:        "tr_customer_service_000003"
state:     {"account": {...}, "orders": [...], "thread": [{"role": "customer", "text": "...got a Bluetooth speaker instead..."}]}
questions: {"category": {"type": "choice", "instructions": "What is this customer conversation primarily about?",
                         "criteria": {"delivery": "Shipping, fulfilment or delivery of a physical item.", ...}},
            "urgency":  {"type": "score", "criteria": ["No time pressure; ...", "Routine; ...", "Elevated; ...", "Critical; ..."]}}
gold:      {"category": {"label": "delivery", "probabilities": {"delivery": 0.95, "account": 0.027, ...}},
            "urgency":  {"label": "2",        "probabilities": {"2": 0.633, "3": 0.3, "1": 0.067, "0": 0.0}}}
6

Fine-tune the heads, not the model

Training embeds every state and option once with the frozen encoder, using the same prompts and truncation as serving, then trains only the state and action heads. On a laptop with the 1B encoder, embedding is the slow part and training takes minutes.

# text + label rows, one question
clm-train --data tickets.csv --question "Which team should handle this?" --options options.json \
    --group-column customer --encoder nemotron-3-embed-1b --out runs/tickets

# typed rows, many questions per state (this page's results)
clm-train --data LocalLLaMA/typed-decisions --workflow all --encoder nemotron-3-embed-1b --out runs/typed-1b

Data formats, splits, outputs and every option are on the training page.

clm-train optionDefaultChange it when
--targets soft|hardsoftUse hard only if you have single labels and no annotator distribution.
--loss infonce|softceinfonceinfonce contrasts against every option text in the batch, which helps when option sets differ between questions. softce only compares a question's own options; try it when one fixed option set dominates.
--width, --depth512, 2 under 3,000 examples; else 1536, 3Rarely. The default follows the data size: on 300 examples the larger head swung between 82% and 95% across runs, the smaller one between 88% and 96%.
--epochs, --patience20, 5The best epoch by validation accuracy is kept as best_head.pt; raise patience for noisy labels.
--encodernemotron-3-embed-8bMust match the encoder you'll serve with. Heads don't transfer between the 1B and the 8B.
--group-columnAlways, when rows share a customer, account or incident

The head maps texts to vectors; it never learns a fixed list of keys. So it will score questions and option wordings it never saw, but nothing guarantees that transfer. Before relying on new options, measure them on labelled examples.

8

Calibrate before anything acts on a probability

  • Temperature. Every request takes temperature, which divides the logits. Pick the value that minimises log-loss on your validation split, then send it on every call.
  • Thresholds for noul. Choose the cut-off that gives the precision you need on validation; 0.5 is rarely right.
  • Abstain on low confidence. confidence is the top probability minus the mean of the others. Route anything below your validation-chosen floor to a person.
9

Serve the head

clm-serve --encoder nemotron-3-embed-1b --ckpt runs/typed-1b/best_head.pt    # now the default model is clm-latest

r = CLMClient().system_one(state, questions, temperature=T)                  # T from step 8

If you change any option text after training, re-run the evaluation. The head scores whatever text you send, and nothing warns you that the wording drifted.

SymptomLikely causeChange
Raw mode picks the option that shares words with the stateThe retriever rewards lexical overlapReword options around evidence, not topic words; then train a head
The right option is usually secondTwo descriptions overlapMake them mutually exclusive; split the question or merge the options
The head beats the majority baseline only slightlyLabels depend on facts outside the state, or classes are imbalancedAdd the missing fields to the state; check per-question accuracy

Accuracy drops on long inputsThe state was truncated from the frontMove decisive content to the end or trim the boilerplate

Labels are subjective and annotators splitHard targets are fighting real ambiguityKeep the distributions; train with --targets soft

What you can't tune: the encoder's weights, its query: / passage: prompts, and its pooling. Changing any of them means a different encoder profile and newly trained heads.
